## Goal

Build a Goose provider that treats an ordinary persistent ChatGPT conversation as recoverable provider-side working state instead of treating one browser render as a reliable transport or creating a fresh Temporary Chat for every Goose turn.

**Core persistence invariant:** within the provider layer, the actual persistent remote object is the server-side ordinary ChatGPT conversation identified by its canonical `/c/<uuid>` conversation ID. Goose remains canonical for the logical transcript and context lifecycle; BrowserHost tabs, renderer processes, Playwright/CDP handles, and launcher process memory are disposable views onto the remote conversation. Losing or replacing any such view must preferentially reopen the same canonical conversation and must never, by itself, cause epoch rollover. This invariant supersedes any earlier rebuild reasoning that accidentally treated retained-tab/process lifetime as remote-conversation lifetime.

The design is intentionally conditional. A blocking protocol spike must first prove the external ChatGPT/connector contracts on which persistence depends. If those contracts fail, revise the architecture rather than patch around them.

## Authority model

Goose remains canonical for:

- logical session and model-visible canonical history projection;
- tools, approvals, delegation/subagents, recipes, and project execution;
- Goose compaction, truncation, branching/resume, and context lifecycle.

CGW owns only provider-local state required to operate and recover ChatGPT Web: remote conversation epochs and identities, canonical-history watermarks, turn lease/recovery state, request journal state, connector evidence, browser binding/diagnostics, and capacity reservations. It must not become a second Goose transcript or tool/delegation authority.

A paired ChatGPT conversation may continue only while its model-visible history remains safely compatible with the paired Goose session. If Goose history becomes non-append-compatible, do not create a replacement provider epoch under the same Goose session; transition the pair toward a deliberate handoff and start a fresh Goose/ChatGPT pair together.

## Paired Goose/ChatGPT conversation lifecycle

Model the provider mapping as one context pair:

```text
Goose session
  └─ one persistent ordinary ChatGPT conversation
```

The pair remains together until a deliberate handoff. Browser/view failure, elapsed time, local conversation-budget estimates, repeated continuation recovery, or an observation failure must not create a replacement ChatGPT conversation while the existing Goose session continues.

For each completed Goose turn, persist the deterministic digest/watermark needed to verify that provider-visible history remains compatible with Goose's canonical projection. If context health or a non-append-compatible Goose history change means the pair can no longer safely continue, request/obtain a handoff and start a **fresh Goose session and fresh ChatGPT conversation together** from that handoff. Do not repair context divergence by independently rolling only the remote provider conversation.

Current epoch/rollover code predates this decision and is implementation debt. Follow-up work must retire or narrow it so remote-chat creation happens only as part of initial pair creation or deliberate paired handoff, as specified by `docs/persistent-chat-lifecycle.md`.

## Cross-chat memory isolation

Use the dedicated `CGW Provider Sessions` ChatGPT Project with project-only memory. Each remote conversation/epoch is still one isolated Goose provider session, and Project instructions explicitly require the model to ignore sibling conversations and Project memory from them.

This is a **behavioral correctness contract, not a security boundary**. OpenAI Project semantics permit sibling-chat reference in principle. Gate 0 observed one clean A→B canary non-leak on a cold Project and no sibling-canary disclosure in additional incomplete/truncated probes. That is sufficient to admit the topology into later qualification, not to claim technical isolation. Nothing intentionally written to these chats may require confidentiality stricter than "acceptable as durable history on this user's ChatGPT account."

Gate D/I must repeat isolation testing after Project memory has aged across many sessions, use adversarial sibling-memory elicitation with synthetic canaries, cover cross-epoch/post-rollover chats, and include an authorized no-isolation-instruction control. Any observed bleed is a blocking correctness defect and immediately disables new shared-Project provider sessions. Fallbacks to qualify in advance are: one project per Goose session/epoch, a supported configuration that disables cross-chat reference, or another observed memory-off topology. Do not patch around a leak with stronger wording alone.

Do not silently change account-wide memory settings. Do not use files/Library as Project context. Persist the Project `gizmo_id` independently of its human-readable slug so browser recovery does not depend on the Project name.

## Component boundary

Keep the appliance small:

1. **Responses facade** — Goose-facing Responses/provider surface.
2. **Session Broker** — paired Goose/ChatGPT mapping, persisted turn lease, capacity queue, request journal, recovery state, and paired-handoff state.
3. **Browser Controller** — Electron/Playwright for authentication, create/open conversation, prompt submission, model/effort selection, reload/rebind, and diagnostics. It owns disposable views, not durable conversation identity.
4. **Connector Gateway** — fixed-schema ChatGPT tool/MCP path to Goose/CGW.
5. **Deterministic Reconciler** — classifies remote/browser/connector evidence and executes bounded recovery transitions.

Do not add an LLM watcher/arbiter in the initial architecture. Ambiguous states end in persisted `UNCERTAIN`/human escalation rather than a model deciding whether to resend or roll over.

## Browser and connector are different planes

The key refinement after adversarial review is to avoid two competing full-content writers.

### DOM/content plane

The persisted ChatGPT assistant message is the remote **content plane**. DOM quiescence is not evidence that server-side generation stopped, but after reload/rebind the logically anchored assistant block is the representation of what the remote conversation persisted.

Reuse/adapt upstream's hard-won browser mechanisms where their semantics fit:

- logical `data-turn-id` anchoring and fail-closed missing/duplicate identity handling. **Requirement 2 — ABSOLUTE TURN ANCHORING**: at accepted send durably bind the absolute user `data-turn-id` when materialized, alongside submit nonce/correlation. On reopen derive assistant identity from the persisted user turn and freshly loaded document/order. Preserve fail-closed duplicate/missing/>1 identity rules and require a deterministic recovery path if virtualization temporarily omits the anchor; never guess by text/title alone.
- accepted-but-unbound prompt must never be blindly resent;
- response-page rebind and completion fencing;
- control-liveness probes that do not impose a generation deadline;
- selector/error diagnostics and redacted captures;
- connector selection handling and effort/model discovery;
- prompt-attachment/chunk acknowledgement guards;
- rate-limit/subscription/upstream-error classifiers;
- Electron packaging, authenticated profile/login, tunnel setup, capacity checks, and browser tests.

### Connector/control-evidence plane

Do not assume a server-to-client push channel. ChatGPT publications are tool/MCP calls initiated by the model. Gate 0 proved that an already-running connector call survives hard refresh and complete page removal. Transport-loss calls were redelivered at roughly the hosted timeout boundary (~121 s in the qualified runs) with the same normalized tool arguments while JSON-RPC `requestId` changed. Treat that timing as observation, not API contract: recovery still cannot depend on either connector silence or a retry arriving.

The target is a small fixed Goose-native surface. Exact names are deferred to Gate A, but the control/evidence functions should be no broader than needed for:

- bounded recovery checkpoint publication;
- final digest/summary publication;
- exact current-turn Goose tool dispatch and Goose-native approval rendezvous.

A checkpoint may carry a bounded self-contained user-visible recovery summary, digest, and pointer/watermark. Do **not** duplicate unrestricted final prose through both the connector and DOM. Full duplicate prose creates an ordering/merge problem and accelerates remote-context growth. A final publication should primarily attest a digest and bounded summary of the intended visible final.

Connector absence is **no evidence of death**. The qualified Project/connector permission state executes calls without a per-call rendered approval. If permissions are revoked or an approval surface reappears, that becomes an explicit `HUMAN_REQUIRED`/`UNCERTAIN` state. The rebuild does not use current upstream's closed-page approval resolver as terminal authority and never auto-answers Allow or Deny.

### Requirement 1 — APPROVAL FENCE
Before any recovery navigation, refresh, reopen, or renderer reset, detect a rendered connector/tool approval/permission surface. If present -> `HUMAN_REQUIRED`, retain conversation lease, no reset/navigation. Gate E/H must qualify what page loss does to pending approval before escalation may operate through one. A rendered approval surface is a hard stop for all autonomous recovery operations; the conversation lease is retained across the halt.

## Security and capability model

Model-visible identifiers must be correlation, not authorization.

- A per-turn `turn_ref`/equivalent may identify the active Goose turn to the connector, but possession of that value alone must not grant local command/file/tool authority.
- The ChatGPT-reachable connector path requires a host-granted transport boundary independent of model-visible correlation values. The selected rebuild boundary is a **dedicated second loopback HTTP listener in the same provider process**, separate from the Goose Responses listener and protected by a distinct owner-only file-backed bearer injected by tunnel-client. Authorization is checked before path/MCP handling; unauthenticated/wrong-bearer traffic gets a content-minimal `401`; no permissive CORS surface is exposed. MCP is stateless JSON-response Streamable HTTP with transport session/resumption/event replay disabled, so the broker `op_ref` journal remains the only operation replay authority. Gate 0 proved the bearer-injection/`401` transport property; process-private stdio remains qualification evidence, not the selected production topology. Same-user processes remain inside the documented local trust boundary.
- Goose still validates the active turn, current advertised registry, approvals, and request correlation before executing anything.
- Capability lifetime follows the **remote server-side turn**, not an Electron page. Refresh/rebind must not revoke an otherwise live remote turn.
- Stale turn references fail closed with an actionable recovery result; earlier refs remaining in persistent history must not be accepted.

Loopback alone does not isolate another malicious process running as the same OS user. Prefer a separate service identity/restricted socket boundary where practical; otherwise document same-user local execution as inside the trust boundary.

**CDP/DevTools control-plane boundary:** Electron's `--remote-debugging-port`/DevTools loopback endpoint (what Playwright's `connectOverCDP()` attaches to, distinct from the MCP/connector transport above) is unauthenticated at the DevTools protocol layer. Any local process that can reach that loopback port gets full CDP control of the owned renderer — including its authenticated ChatGPT session, cookies, DOM, and arbitrary JS execution. MCP/tunnel bearer authorization protects only the dedicated connector listener; it provides no protection whatsoever to the CDP endpoint and must never be read as doing so. For the initial rebuild this endpoint is accepted as inside the same documented same-user local trust boundary as the rest of the appliance, conditioned on: binding strictly to loopback (never a LAN-reachable/`0.0.0.0` interface) with no remote port-forward/tunnel exposure of the debugging port; keeping the listening surface/lifetime minimal where practical for the selected Playwright architecture; and Gate B verifying and documenting the bound interface, exposure, and lifetime. Electron 41.10.7 starts this listener from process-start command-line switches and does not withdraw or move the live listener when those switches are later removed/re-added, while the qualified BrowserHost control path requires Playwright `connectOverCDP()`. Therefore **process lifetime is the minimum practical initial listener lifetime without replacing the selected DOM-control architecture**; a future authenticated/non-TCP or separate-service control transport may tighten this boundary, but is not a Gate B prerequisite unless new evidence invalidates the accepted same-user trust model. A same-user malicious process with loopback access still has full CDP authority regardless of these mitigations — that residual risk is the same same-user boundary already accepted above, not a new one, and it must not be conflated with the connector's model-invisible transport-authorization guarantee.

### Durable remote-data exposure

Persistent chats retain connector tool calls/results and assistant history on ChatGPT's servers. This is materially different from Temporary Chat. Before production qualification define and test:

- result-size limits;
- credential/secret redaction;
- handling of private source/file/command output;
- remote chat retention/archive policy;
- what data is intentionally allowed to become durable server-side history.

**Initial Gate B durable-data policy (local foundation; real ChatGPT persistent transport is not enabled yet):** every future tool result crossing into persistent ChatGPT history must pass the rebuild-owned `persistent-remote-data` boundary rather than legacy diagnostic sanitizers. The caller must explicitly classify the result as `task`, `public`, or `sensitive`. Only text classified `task` or `public` may pass; `sensitive`, structured/binary/image content, and NUL-bearing output fail closed. Before release, known credential forms (including bearer/API/GitHub/Slack/AWS tokens, credential-bearing URLs, password/secret/token/cookie assignments, and private-key blocks) are redacted, then the persisted UTF-8 result is capped at **32 KiB** with an explicit truncation marker. `task` means local source/file/command text intentionally required to execute the user's task; it is not a declaration that the material is public. Browser-profile/auth state, cookies, credentials/keys and other explicitly sensitive material are never eligible merely because a tool can read them. Pattern redaction is defense in depth, not authority to read secret sources: callers must classify known-sensitive output as `sensitive` and local tool/approval policy remains authoritative. The local rebuild connector gateway now applies this boundary before its durable terminal journal commit; Gate E must prove the same path through the real ChatGPT persistent connector before side-effecting tool qualification, and Gate I adversarially validates/tunes the patterns and size ceiling against real retained history.

Initial retention posture is conservative: active or `UNRECONCILED` provider conversations are never auto-archived/deleted because they remain recovery evidence/liability. A provider conversation becomes archive-eligible only after its Goose/ChatGPT pair has completed a deliberate handoff and all local replay/recovery obligations are closed; no automatic remote deletion is authorized. Until Gate I qualifies the actual archive/retention behavior, controlled qualification uses intentionally non-sensitive task material and treats remote chat history as durable.

## Persisted remote-turn lease

Concurrency is controlled at the remote turn, not at the browser page.

Persist one lease per paired `(Goose session, remote conversation)` with three core states:

- `IDLE` — a new Goose turn may be admitted to the paired provider chat;
- `TURN_OUTSTANDING` — a Goose turn is accepted or may be executing server-side;
- `UNRECONCILED` — the current turn needs recovery/reassessment before a new Goose turn may be admitted.

A page crash, controller restart, stale DOM, helper-heartbeat loss, refresh failure, or other browser-view problem does not release or abandon the paired conversation lease. `UNRECONCILED` is a recovery state, not a terminal chat state: retain the canonical conversation and recover an interactive view until the turn either completes, needs an internal same-chat continuation, or the chat deliberately produces a paired handoff. Never use elapsed time or browser silence to authorize original-prompt resend or retirement of the persistent ChatGPT conversation.

The account execution slot and browser resources are separate from conversation identity. A stale/dead browser view may be refreshed or discarded and its local resources reclaimed without abandoning the persistent conversation. Any slot-release policy must preserve enough durable state to resume the same canonical chat safely; it must not turn resource cleanup into provider-chat death.

Initial appliance capacity is one active ChatGPT-Web execution per account. Multiple Goose sessions use an explicit broker/FIFO queue. Queue time is not charged against browser-stage deadlines. The account mutex remains a capacity/risk boundary, but queue/resource management must conform to the recovery invariants in `docs/persistent-chat-lifecycle.md`.

## Identity and orphan recovery

Persist the canonical ChatGPT conversation id from `/c/<uuid>` as remote identity, together with Project `gizmo_id`, Goose session/epoch, and canonical-history watermark. ChatGPT briefly exposes a provisional `/c/WEB:<uuid>` immediately after accepted send; Gate 0 proved that provisional URL is not a durable locator and must be replaced when the canonical UUID appears.

Record a durable pre-submit intent with a non-secret unique nonce before the first mutation. Gate 0 proved the crash-orphan window by terminating Electron after the user turn was visibly accepted but before reading/persisting its URL. After restart, ChatGPT's `conversation-history` cache exposed a new canonical id with matching creation window and Project metadata; opening only that candidate verified the nonce-bearing user turn and final assistant response.

Recovery may use that observed conversation index as a candidate source, but never as unverified authority. Filter by expected Project, creation window, and local intent, then open the candidate and verify the nonce/correlation in the actual persisted conversation. If the cache shape is unavailable, fall back to the user-facing in-app Project chat list/search enumeration and apply the same open-and-verify rule. Missing, stale, or multiple candidates (including concurrent human account use) become `UNRECONCILED`; persist the possible unknown remote turn as a liability and never resend the accepted prompt to discover which chat was created. The remote-turn lease remains held across controller restarts throughout this recovery.

- **Requirement 12 — Preserve ownership fail-closed**: exact owned surface/target identity, never URL alone; 0 or >1 ownership candidates fatal. Gate D must either qualify DevTools target-id behavior across renderer reset or define target-id + re-injected surface marker + canonical URL as the deterministic replacement identity contract before real reset.
Reopen/reconcile must distinguish at least: found/current, still-running, complete, not-found/deleted, archived, authentication/workspace mismatch, and structurally ambiguous identity. Ambiguity becomes `UNRECONCILED`; it is never treated as permission to resend.

## Journal and crash consistency

Reuse the proven Goose Pilot RequestJournal **contract**, not Goose Pilot as a runtime dependency: durable claim before side effects, conflict detection, terminal `SUCCESS` / `FAILURE` / `UNCERTAIN`, exact replay of known terminal outcomes, no blind redispatch of an ambiguous mutation, crash-safe stale-owner recovery, and fsync before success acknowledgement.

OpenAI does not provide the logical operation identity required for those guarantees. Gate 0 found JSON-RPC `requestId` overwhelmingly reused, `_meta.openai/session` useful only as scope, and SDK `sessionId`/`taskId`/`requestInfo`/`authInfo` null. In controlled transport-loss runs, the eventual redelivery recomputed the **same normalized input hash** as the original while `requestId` changed `0 → 1`; raw wire-byte equality was not recorded.

### Gateway-owned `op_ref`

Initial connector mutation dispatch is serial within one remote turn. Before the model may submit a side-effecting connector operation, the gateway mints an opaque non-secret `op_ref` scoped to `(Goose session, epoch, turn_ref, monotonic op sequence)`, fsyncs it as `MINTED`, then makes it model-visible through gateway-authored turn context or the previous tool result. `op_ref` is **identity/idempotency only, never authorization**; the independent transport boundary and Goose permissions remain authoritative.

Journal key and state are at least `{op_ref, turn_ref, seq, input_hash, state, result, owner, timestamps}` where state includes `MINTED`, `CLAIMED`, terminal outcome, and `UNCERTAIN`.

Admission rules:

1. A valid `MINTED` ref is atomically/fsync transitioned to `CLAIMED` with its normalized input hash **before** any side effect; execute once; fsync the terminal result before returning it.
2. The terminal response includes the already-fsynced **next** `op_ref`. A legitimate later identical operation is therefore distinct because it carries that fresh ref. If the result never reached the model, the model does not possess the next ref and can only repeat the old operation.
3. Same `op_ref` + same input while a live owner exists attaches single-flight to that execution; it never starts a second worker.
4. Same `op_ref` + same input after owner loss with only `CLAIMED` durable returns `UNCERTAIN` and never redispatches. Same ref after terminal commit replays the exact recorded result without reapplying the effect.
5. Same `op_ref` + different input is `OP_REF_CONFLICT`. Unknown, unminted, wrong-turn, future/out-of-order, or expired refs fail closed and never execute.
6. A side-effecting call without a valid ref never executes. If its input matches a recent unresolved/just-terminal operation in the same turn, classify it as suspected redelivery/`UNCERTAIN`; otherwise reject it as invalid. Gate E qualifies the retention/suspicion windows from real traffic.
7. Old terminal refs remain replayable for a bounded post-terminal redelivery window, then become `STALE_OP_REF`. Persistent chat history therefore cannot reactivate old authority.

A terminal journal commit advances local operation state; successful transport delivery is not the durability boundary. False `UNCERTAIN` is possible if an effect occurred immediately before a crash, but false `SUCCESS` and double execution are not acceptable outcomes.

The Gate 0 deterministic acceptance using the same MCP server code proved the underlying state machine: duplicate `SUCCESS` replay produced exactly one effect total, while a process death with only `CLAIMED` durable returned `UNCERTAIN` with zero redispatch. The local rebuild gateway additionally proves same-process single-flight attach, client-disconnect independence, and `UNCERTAIN` retention when either rendezvous or terminal journal commit fails. Gate E must now prove that ChatGPT reliably echoes the minted `op_ref` on the real connector path; failure to do so revises the identity mechanism before real Goose side effects are enabled.

**Goose Responses tool-continuation identity:** the facade persists no prompt/tool-result text for request classification. The initial broker turn atomically stores a versioned digest-only projection checkpoint: full request hash, non-`input` hash, canonical input hash, and input-item count. During an active tool round, an identical current request is transport replay. A tool-result continuation is accepted only when the next Goose request preserves the exact prior non-input projection and canonical input prefix, then appends exactly the provider-issued `function_call` `(call_id = op_ref, exact tool name, exact literal arguments string originally emitted by the facade)` plus one matching string `function_call_output`. The facade canonicalizes arguments once for dispatch and retains that exact emitted string for comparison; it must not reserialize later and assume byte-equivalence. Anything else fails closed as divergence. After acceptance the digest checkpoint advances to the new full projection, so serial tool rounds compose without turning POST count into identity. The immutable initial `requestHash` still maps delayed replay to the existing logical turn and never rewinds the mutable progress checkpoint.

**Process-local Goose tool baton:** `GooseToolRendezvous` is intentionally in-memory and must share the exact provider-process lifetime with the sole SessionBroker owner. Before releasing a provider-authored `function_call` to the current Goose Responses request, it installs the expected continuation containing the live `op_ref`, tool name, exact emitted argument string, prior durable projection checkpoint, and blocked connector result. Therefore a fast Goose tool-result POST cannot outrun its waiter. On the matching next POST, durable broker progress advances first; only then is the new current Goose stage installed, and only after that may the previous connector call be released back to ChatGPT. Process loss destroys all raw tool dispatch identity; broker restart converts durable `CLAIMED` work to `UNCERTAIN`, and neither hashes nor persistent chat history may be used to reconstruct/re-emit the lost function call. If execution may have happened but the atomic progress/terminal commit fails, the gateway also durably marks the turn `UNRECONCILED` while the operation remains `CLAIMED`; the process-local baton quarantines that turn for the remainder of the provider process. That baton quarantine intentionally has no independent clear operation: a provider-process restart destroys all stale raw stage authority and lets broker restart recovery convert the claim to `UNCERTAIN` before any verified remote rebind. A Responses stage opened outside an active continuation must exactly equal the broker-owned current digest checkpoint, so released stages cannot allow stale pre-tool history to become current again. Once a tool-call stage has been emitted, a delayed replay of that older Goose POST fails closed rather than receiving the function call twice; Goose `call_id` de-duplication is not assumed.

## Completion contract

Do not let either DOM cosmetics or model compliance alone declare completion.

Preferred completion requires a conjunction:

1. connector final digest/summary is durably acknowledged when that mechanism is available;
2. no Goose tool/approval mutation remains unresolved;
3. remote turn is observed non-running after reopen/rebind or another qualified terminal signal;
4. logically anchored final assistant content matches the acknowledged digest.

A late redelivery carrying a previously terminal `op_ref` is benign journal replay even if it arrives after visible final content; it does not reopen the turn or count as fresh connector activity. A **fresh** side-effecting operation after accepted final, or a ticketless/conflicting call, is a protocol violation and escalates. Digest mismatch is `UNRECONCILED`, not a merge problem.
- **Requirement 9 — Tool-dispatch answer-boundary rendezvous**: when the real connector first presents a valid `MINTED` `op_ref`, `BOUNDARY_REQUIRED` is non-mutating. Before claim, the connector gateway single-flights one injected boundary preparation for that `op_ref`; preparation must freshly re-observe the exact authenticated/canonical persistent surface after the qualified renderer catch-up/quiescence condition, capture the current assistant answer projection, and durably record that boundary. A cached DOM read is not sufficient. Only then may the gateway re-run `claimOperation`; boundary observation/recording failure leaves the operation `MINTED` and authorizes no side effect. After final tool result, completion requires new assistant content beyond that boundary or explicit qualified terminal semantics. Prevent truncated post-tool final answers.
- **Requirement 10 — Completion fence durable monotone CAS**: begin at revision N, force fresh remote/DOM observation, commit only if revision unchanged and no unresolved tool/approval/activity exists; retain tombstones so delayed claims cannot resurrect work after completion; fsync durable broker state around terminal transition.

## Recovery state machine

Recovery manages the **browser view and current turn inside the same persistent ChatGPT conversation**. It does not decide whether the conversation should be abandoned or replaced; those lifecycle invariants are owned by `docs/persistent-chat-lifecycle.md`.

Minimum operational states are:

- `QUEUED` — account capacity reserved; Goose turn not submitted;
- `ACTIVE` — the current ChatGPT turn is visibly/server-evidently still working;
- `VIEW_STALE` — the browser view is no longer trustworthy enough to classify the remote turn;
- `CONTINUATION_REQUIRED` — a fully settled view shows the current turn stopped/errored before the intended final answer;
- `UNRECONCILED` — exact current-turn state still needs recovery/correlation before another Goose turn may be admitted;
- `HUMAN_REQUIRED` — authentication, approval, security, or another genuinely human boundary blocks autonomous recovery;
- `HANDOFF_REQUIRED` — context health indicates the paired Goose/ChatGPT chats should close at a safe checkpoint and produce a handoff;
- `COMPLETE` — the intended final has been reconciled and delivered to Goose.

Recovery rules:

1. **Browser/DOM evidence describes the view, not the durable conversation.** A missing turn container, stale renderer, page error, helper-heartbeat expiry, Playwright/CDP failure, or elapsed observation budget may mark the view stale and trigger recovery. None is permission to abandon the provider chat, resend the original Goose prompt, or start another ChatGPT conversation.
2. **Prefer hard refresh of the same owned view.** Disconnect fragile observation state as needed, issue the hard refresh, and wait until the new document has fully loaded/hydrated and reached a stable classifiable state before taking another recovery action. Do not run a refresh death loop. A later refresh is justified only if the settled view subsequently becomes stale again.
3. **A settled working view returns to observation.** When the refreshed view shows ChatGPT actively generating (for example the current Stop control/running indicator), let the same server-side turn continue. Do not send a continuation while it is still working.
4. **A settled stopped/error view with no intended final requires continuation.** Recognized error UI such as generation timeout/try-again, or a fully settled non-running view whose composer has returned to the ordinary idle control while no final answer was produced, transitions to `CONTINUATION_REQUIRED`. Never click ChatGPT Retry. Send the standardized GCW-internal continuation in the same conversation and resume observation.
5. **Continuation is repeatable.** The continuation prompt is not a Goose turn and is never projected into Goose canonical history. It may be sent again after later fully settled stopped/error states as often as needed to obtain the intended final. Never resend the original accepted Goose prompt.
6. **Connector/tool evidence remains authoritative for Goose-side work.** Connector activity can prove progress even when the browser view is stale. Unresolved tool/approval/operation state remains fenced exactly as required by the journal; view recovery must not duplicate side effects.
7. **Timers and heartbeats are watchdogs only.** They may trigger view inspection/refresh and diagnostics. They do not prove remote death or completion and cannot release the persistent chat by themselves.
8. **A truly dead browser surface is replaceable; the conversation is not.** If hard refresh cannot operate because the owned tab/renderer no longer exists, replace only the disposable BrowserHost surface and rebind to the same canonical conversation. This is a view reconstruction fallback, not a new provider chat or epoch.
9. **Repeated continuation recovery raises context pressure.** Track it across Goose turns. A tunable threshold (initially about three Goose turns requiring continuation recovery) may transition the pair to `HANDOFF_REQUIRED`; exceeding the threshold does not abandon the current chat.
10. **Handoff is paired.** The current ChatGPT conversation should finish a bounded safe checkpoint and produce a handoff. Then start a fresh ChatGPT conversation and a fresh Goose session together from that handoff so provider and Goose context remain aligned.

The following safety requirements remain load-bearing under this lifecycle model:

- **Requirement 5 — Recovery navigation interlock:** while a Goose turn is `ACTIVE`, `VIEW_STALE`, `CONTINUATION_REQUIRED`, or `UNRECONCILED`, only the recovery state machine may reload, navigate, replace, or reset the owned ChatGPT browser surface. UI chrome, idle-return logic, challenge/background handlers, or other code must not mutate that surface independently. A local view reset never proves the server-side turn stopped and never authorizes original-prompt resend.
- **Requirement 7 — Sleep/suspension is load-bearing:** retain the power-save blocker while a remote browser turn is active; detect suspend/sweep gaps; and refund/re-baseline observation, recovery, and browser-lease timers after resume. Sleeping time must not be charged as failure or used to trigger a continuation/refresh prematurely.
- **Durable recovery counters:** persist enough recovery state with the paired conversation/turn lease that controller restart cannot reset refresh attempts, in-turn continuation attempts, or the cross-Goose-turn signal that recent turns required continuation. Exact windows/thresholds are tunable, but restart must not erase context-pressure evidence or create a refresh/continuation loop.
- **Requirement 17 — One-surface FIFO handoff fence:** repoint the one owned browser surface from session A to session B only after A's current Goose turn is durably complete, or A has reached another explicitly qualified idle/handoff boundary with no active ChatGPT generation, continuation pending, unresolved tool/approval/activity, or completion-CAS claim. Never switch because of timeout, queue pressure, heartbeat loss, or a stale browser view. Switching the disposable surface must never abandon A's canonical ChatGPT conversation.

Exact DOM selectors, refresh-settle predicates, stale-view timers, and the continuation-recovery threshold are tunable qualification parameters. They may evolve without changing the lifecycle invariants above.
